## 1. 项目概述

### 1.1 项目背景：三股力量正在重塑跨境行业

**力量一：平台从"单点"变成"矩阵"。**
一个中等规模卖家通常同时运营 3–8 个店铺，横跨 Amazon US、Shopee 六国站点、Lazada、TikTok Shop。每个平台一套后台、一套商品模型、一套订单状态机、一套费率规则。人工在多个后台之间切换对账，是目前最昂贵的隐性成本。

**力量二：低值包裹免税时代终结，合规从"成本项"变成"生死项"。**
这是 2025–2026 年最剧烈的变化，直接决定了本产品的形态：

| 时间 | 市场 | 政策变化 |
|---|---|---|
| 2025-05-02 | 美国 | 取消中国及中国香港原产货物的 Section 321 免税资格（含经第三国转运） |
| 2025-08-29 | 美国 | 免税资格暂停范围扩大至所有原产国 |
| 2026-02-24 | 美国 | 800 美元 de minimis 门槛全面取消，每个包裹均需正式报关、HTS 归类与全额缴税 |
| 2026-01-01 | 泰国 | 取消 1,500 泰铢以下包裹免税，自第一泰铢起征 7% VAT + 分级进口关税 |
| 2026-01-01 | 马来西亚 | 所有商业包裹无论货值一律征收 10% 低值商品销售税 |
| 2026-04-08 | 印度尼西亚 | 价值超 100 美元的跨境包裹强制征收 11% PPN 及适用关税 |
| 2026-07-01 | 越南 | 新税收管理法生效，税费由平台代扣代缴，直邮每单加收 10,000 越南盾清关手续费 |
| 2026-03 | 中国—东盟 | 跨境电商零关税补充协定生效，98% 商品享零关税，清关时效由 48h 压缩至 24h |

**结论**：过去"卖一单算一单毛利"的粗放算法已经失效。**落地成本（Landed Cost）必须在选品阶段、定价阶段就被精确计算出来**，否则会出现"卖得越多亏得越多"。这就是本产品与市面上一批"订单搬家工具"的根本区别。

**力量三：利润被平台费率、广告费、汇率、退货四重挤压。**
平台佣金、支付手续费、广告 ACOS、跨境汇损、退货损耗分散在不同后台，卖家很难定位"到底是哪个 SKU 在亏钱"。真正赚钱的卖家靠的是**SKU 级盈亏核算能力**，而不是运营勤奋度。

### 1.2 产品定位与价值主张

> **一句话定位**：为多平台跨境卖家提供"一处管全部"的运营中台——把散落在 6 个平台后台的数据统一归集，用**合规前置**和**SKU 级利润核算**帮卖家算清每一单到底赚不赚钱。

**三个核心价值支柱**：

1. **统一归集**：一次授权，多平台商品、订单、库存、广告、财务数据自动同步到一处。
2. **合规前置**：内建 HS 编码库、Landed Cost 引擎、各国认证台账，在选品与刊登阶段就拦截合规风险，而不是等货物被海关扣了才发现。
3. **利润透明**：从采购价一路算到净利，精确到 SKU × 站点 × 币种 × 日。

**与传统 ERP 的差异定位**：

| 维度 | 传统跨境 ERP（如通用铺货工具） | CrossPilot |
|---|---|---|
| 核心逻辑 | 订单与库存搬家，追求对接平台数量 | 归集 + 算账，追求数据准确性与利润可视性 |
| 合规定位 | 事后提示/人工台账 | 事前拦截（刊登前校验 + 定价前算税） |
| 利润模型 | 简单毛利公式 | 全成本模型（含关税、报关费、汇损、退货摊销） |
| 数据架构 | 单租户部署为主 | 原生多租户 SaaS |
| 面向对象 | 铺货型大卖家 | 精品/品牌型卖家 + 中小团队 |

### 1.3 目标用户与角色画像

| 角色 | 典型画像 | 核心痛点 | 对本产品的核心诉求 |
|---|---|---|---|
| 店主 / 老板 | 年 GMV 500 万–5000 万，管 3–8 个店铺 | 看不清真实利润，不知道哪个 SKU 在亏 | 经营看板、SKU 盈亏榜、现金流预测 |
| 运营主管 | 带 2–5 人小团队，日处理 200–2000 单 | 多后台切换、手动改价改库存、易出错 | 批量操作、任务看板、异常预警 |
| 运营专员 | 负责 1–2 个站点，做刊登与活动 | 刊登字段繁琐、多语言难、类目属性对不上 | 批量刊登、翻译辅助、模板复用 |
| 采购 / 供应链 | 对接工厂与货代 | 库存与在途不清、补货靠拍脑袋 | 采购建议、在途跟踪、库存水位预警 |
| 财务 | 兼职或外包会计 | 多币种对账、平台账单口径不一 | 自动对账、利润表、汇兑损益 |
| 客服 | 多时区轮班 | 多后台看消息、超时被罚 | 统一消息中心、SLA 倒计时、模板回复 |

### 1.4 竞品分析与差异化切口

| 竞品类型 | 代表 | 优势 | 弱点（我们的机会） |
|---|---|---|---|
| 国内跨境 ERP | 通用铺货型 ERP 工具 | 平台对接全、价格低 | 合规能力浅、利润模型粗、界面老旧 |
| 海外 SaaS | 主流电商数据工具 | 数据分析强 | 不贴合中国供应链与采购逻辑、价格高 |
| 建站工具 | 主流独立站 SaaS | C 端体验好 | 不做多平台中台、不做合规与报关 |
| 平台官方工具 | 各平台卖家中心 | 数据最准 | 只管自己一家、无跨平台视角 |

**差异化切口（V1 只打这三枪）**：
1. **Landed Cost 引擎**——把关税、报关费、VAT/GST 算进 SKU 成本，这是 2026 年后最刚需、也最难抄的能力。
2. **SKU 级真实利润**——全成本核算，能明确回答"哪个 SKU 在亏钱"。
3. **合规校验前置**——刊登前就校验认证与禁售，而不做事后提醒。

### 1.5 成功指标

**北极星指标**：周活跃租户数（Weekly Active Tenant，WAT），即一周内至少完成一次有效同步且有成员登录的租户数。

| 层级 | 指标 | V1 目标值 |
|---|---|---|
| 业务层 | 注册租户数 | 50 |
| 业务层 | 付费转化率 | ≥ 15% |
| 业务层 | 租户月留存 | ≥ 80% |
| 产品层 | 授权店铺数/租户 | ≥ 3 |
| 产品层 | 订单同步成功率 | ≥ 99.5% |
| 产品层 | 数据同步延迟（订单） | P95 ≤ 5 分钟 |
| 产品层 | Landed Cost 计算准确率 | 与官方账单偏差 ≤ 2% |
| 技术层 | 核心接口 P95 响应时间 | ≤ 500ms |
| 技术层 | 系统可用性 | ≥ 99.9% |

### 2.2 Out-of-Scope（V1 明确不做）

明确排除是控制范围的关键。以下内容 V1 不做，避免项目膨胀：

| 排除项 | 原因 | 计划版本 |
|---|---|---|
| 自建 C 端商城 / 独立站前台 | 与中台定位冲突，可用现成建站工具 | 不做 |
| 自研 WMS 仓储管理系统（拣货波次、PDA 扫码） | 复杂度极高，V1 用第三方仓 API 对接 | V3 评估 |
| 自研货代/物流轨迹全链路追踪 | 先接第三方聚合 API | V2 |
| 广告自动投放与智能调价算法 | 先做数据看板与手动调价 | V2 |
| AI 自动生成 Listing 全流程 | V1 只做翻译辅助与关键词建议 | V2 深化 |
| 移动端 App | V1 只做响应式 Web | V2 |
| 支付/收款通道直连 | 接入第三方收款服务商 API | V2 |
| 多语言界面（非中文） | V1 界面仅简体中文 | V2 |

### 3.2 关税与税制合规矩阵

**税制参数表**（系统需内置为可配置字典，支持运营后台维护与版本生效日期）：

| 国家/地区 | 税种 | 标准税率 | 低值商品特殊规则 | 起征门槛 |
|---|---|---|---|---|
| 美国 | Sales Tax | 各州不同（0%–10.25%） | Economic Nexus 判定后由平台代收代缴 | 各州 10 万–50 万美元销售额 |
| 美国 | 关税 + MPF | 按 HTS 归类，通常 0%–25%+ | **已无免税门槛**，全部需正式报关 | 无 |
| 新加坡 | GST | 9% | 低值商品（≤ S$400）需 OVR 注册并征收 | 无（低值通道已纳入） |
| 马来西亚 | SST（低值商品销售税） | 10% | 所有商业包裹一律征收 | 无 |
| 泰国 | VAT | 7% | **自第一泰铢起征**，另加分级进口关税 | 无 |
| 印度尼西亚 | PPN | 名义 12%，一般商品有效 11%（DPP = 售价 × 11/12）；奢侈品 12% | 货值 > 100 美元强制征收 PPN + 关税 | 100 美元 |
| 越南 | VAT | 10%（部分商品 5%） | 平台代扣代缴；直邮每单 10,000 VND 清关费 | 依新税收管理法 |
| 菲律宾 | VAT | 12% | 低值包裹已纳入征收 | 无 |

**泰国分级进口关税参考**（2026 年调整后，系统需按 HS 编码实时查表）：

| 品类 | 关税税率 |
|---|---|
| 服装、鞋类 | 约 30% |
| 箱包 | 约 20% |
| 其他（按材质） | 10%–20% |

> ⚠️ **重要实现提示**：以上税率是**系统配置项而非硬编码常量**。税率会随政策变动（如泰国 2026-03-30 宣布计划将塑料制品与电子配件关税上调至 30%–40% 法定上限），系统必须支持"税率表 + 生效日期 + 版本化"，并保留历史版本以便回溯重算历史订单成本。任何税率数据的上线都必须由运营人员核对官方来源后录入，并在界面上标注数据来源与最后更新日期。

### 3.3 三档合规校验模型

系统对每个 SKU × 目标国组合做三档校验，输出红/黄/绿灯：

| 档位 | 校验内容 | 拦截面 |
|---|---|---|
| **L1 准入合规（红灯，拦截）** | 目标国是否禁售该类目；是否已在平台禁售清单；是否需要强制认证而缺失 | 商品刊登前、采购下单前 |
| **L2 认证合规（黄灯，提醒）** | 认证文件是否在有效期内；是否需补充检测报告；标签合规性 | 刊登时提醒、看板汇总 |
| **L3 成本合规（计算）** | 关税税率、VAT/GST、报关费、清关手续费是否已计入成本模型 | 定价时强制计算 |

**各国强制认证要求表**（V1 至少覆盖）：

| 市场 | 认证 | 适用品类 |
|---|---|---|
| 美国 | FCC | 带无线/电子功能产品 |
| 美国 | FDA | 食品、化妆品、医疗器械、激光产品 |
| 美国 | CPC | 12 岁以下儿童用品 |
| 美国 | UL/ETL | 电气产品（部分平台强制） |
| 泰国 | TIS（泰国工业标准） | 电器、玩具、钢制品等 |
| 泰国 | 泰国 FDA | 食品、化妆品、医疗器械 |
| 印尼 | SNI | 电器、玩具、食品接触材料等 |
| 印尼 | BPOM | 食品、化妆品、保健品 |
| 越南 | CR 标志 | 受管制电气电子、玩具 |
| 新加坡 | 安全认证（Safety Mark） | 小家电、充电设备 |
| 马来西亚 | SIRIM | 电气产品 |

## 4. 角色与权限设计

### 4.1 角色定义

| 角色码 | 角色名 | 描述 | 是否可自定义 |
|---|---|---|---|
| OWNER | 租户所有者 | 注册租户的账号，拥有全部权限，可转让 | 否 |
| ADMIN | 管理员 | 除租户注销/转让外的全部权限，管人管配置 | 否 |
| OPS_MANAGER | 运营主管 | 商品/订单/库存/广告全权限，可看全量数据 | 否 |
| OPS_STAFF | 运营专员 | 仅授权店铺范围的操作权限，不可看财务成本 | 否 |
| PURCHASER | 采购 | 采购单、供应商、库存 | 否 |

| VIEWER | 只读访客 | 全模块只读（常用于老板小号/外部顾问） | 是 |

**自定义角色**：ADMIN 可基于上述角色的权限点自由组合，创建自定义角色（V1.5）。

### 4.2 权限模型

采用 **RBAC + 数据范围（Data Scope）** 双层模型：

- **功能权限**：`资源:动作` 形式，如 `order:read`、`order:ship`、`product:publish`、`finance:read_cost`。
- **数据范围**：每个用户对每类资源拥有三种数据范围之一 —— `ALL`（全部店铺）/ `SELECTED`（指定店铺列表）/ `NONE`。

## 5. 端到端业务流程

### 5.1 主流程（Happy Path）

```
① 注册租户
     ↓
② 绑定店铺（OAuth 授权 / API Key 填写）
     ↓
③ 全量数据初始化同步（商品 → 订单 → 库存 → 财务）
     ↓
④ 配置合规参数（目标国、HS 编码、认证台账、税率核对）
     ↓
⑤ 商品管理 → 多语言刊登到多平台（刊登前过 L1/L2 合规校验）
     ↓
⑥ 定价（Landed Cost 引擎算出成本底线 → 加目标利润率 → 生成建议售价）
     ↓
⑦ 增量同步（订单每 1–5 分钟、库存变动实时、广告每 6 小时、财务每日）
     ↓
⑧ 订单处理（归集去重 → 审核 → 匹配库存 → 批量发货 → 回传物流单号）
     ↓
⑨ 库存协同（出库扣减 → 多平台库存同步 → 低于安全水位触发补货建议）
     ↓
⑩ 财务核算（拉取平台账单 → 匹配订单 → 归集费用 → 计算 SKU 级净利）
     ↓
⑪ 经营分析（看板 + SKU 盈亏榜 + 异常告警）
     ↓
⑫ 复盘迭代（哪个 SKU 亏钱 → 调价/停售/换渠道）
```

### 5.2 关键子流程一：订单归集与去重

跨境场景下同一笔订单可能通过轮询 API 与 Webhook 两条路径同时到达，必须保证只入库一次。

```
拉取订单（增量, 按 update_time 游标）
     ↓
生成幂等键：{platform}:{shop_id}:{platform_order_id}
     ↓
查重（Redis 布隆过滤器 + DB 唯一索引双重保障）
     ├─ 已存在 → 比对 update_time → 有变更则更新，无变更则丢弃
     └─ 不存在 → 写入订单主表
                    ↓
              订单明细展开（一个平台订单 → N 条 order_item）
                    ↓
              SKU 匹配（平台 SKU ↔ 本地 SKU 映射表）
                    ├─ 匹配成功 → 关联成本价
                    └─ 匹配失败 → 进入"待关联"队列，触发告警
                    ↓
              状态机推进 + 费用预估 + 触发下游（库存预占、通知）
```

**订单状态机**（统一抽象，屏蔽各平台差异）：

```
PENDING（待付款）
   ↓
PAID（已付款/待发货）
   ↓
SHIPPED（已发货）
   ↓
DELIVERED（已签收）
   ↓
COMPLETED（已完成）

异常分支：
   ├─ CANCELLED（已取消）
   ├─ REFUNDING（退款中）
   ├─ REFUNDED（已退款）
   └─ RETURNED（已退货）
```

> 各平台状态需通过**状态映射表**转换为统一状态。例如 Shopee 的 `READY_TO_SHIP`、Lazada 的 `pending`、Amazon 的 `Unshipped` 都映射到本系统的 `PAID`。映射关系必须可配置，因为平台会新增状态。

### 5.3 关键子流程二：库存同步与防超卖

超卖是跨境最痛的事故（既赔钱又被平台处罚），必须从架构上防御：

```
库存变动事件（入库/出库/退仓/调拨）
     ↓
写本地库存表（原子更新 + 乐观锁 version）
     ↓
发布库存变更事件到消息队列
     ↓
多平台库存分发任务（每个平台独立限流器 + 独立重试队列）
     ↓
可售库存计算：可售 = 物理库存 - 已占用(未发货订单) - 安全库存水位
     ↓
回传各平台（Shopee/Lazada 批量 50 SKU/次，Amazon 走 Feeds 异步）
     ↓
回传失败 → 指数退避重试 → 超过 N 次进死信队列 → 告警
```

**三层防超卖机制**：
1. **库存预占**：订单进入 `PAID` 立即预占库存，不等发货才扣。
2. **安全水位**：为每个 SKU×平台配置安全库存（默认 2 件），实发库存 = 可售 - 安全水位。
3. **同步延迟兜底**：若某平台库存回传延迟超过阈值（如 10 分钟），自动将该平台库存下调至 0 并告警，宁可少卖不可超卖。

### 5.4 关键子流程三：SKU 级利润核算

```
销售流水（平台账单 / Settlement Report）
     ↓
逐项归集：
   ├─ 商品销售额（Product Sales）
   ├─ 平台佣金（Referral Fee / Commission）
   ├─ 支付手续费（Payment Processing Fee）
   ├─ FBA 费用 / 平台物流费（Fulfillment Fee）
   ├─ 广告费（Advertising Cost，按 SKU 分摊）
   ├─ 仓储费（Storage Fee）
   ├─ 促销折扣（Promotion / Coupon）
   ├─ 退款与退货损失（Refund / Return，含货损摊销）
   ├─ 关税与税费（Duty / VAT / GST）
   ├─ 头程物流分摊（First-mile，按重量/体积分摊）
   ├─ 采购成本（COGS）
   └─ 汇兑损益（按实际结算汇率）
     ↓
净利 = 销售额 - 以上全部成本项
     ↓
输出：SKU × 站点 × 日 的净利、净利率、ROI、库存周转天数
```

**核心公式（必须写入代码注释与产品文档，避免口径争议）**：

```
单品净利 = 实收销售额
         - 平台佣金 - 支付手续费 - 平台物流费 - 仓储费
         - 广告费分摊 - 促销折扣
         - 退款退货损失
         - 关税与税费
         - 头程物流分摊
         - 采购成本(COGS)
         - 汇兑损益

净利率 = 单品净利 / 实收销售额 × 100%
ROI   = 单品净利 / (采购成本 + 头程物流分摊) × 100%
```

**Landed Cost 计算模型（核心算法，需精确实现）**

```
输入：
  ├─ 采购价（RMB）
  ├─ 包装后重量（kg）、体积（cm³ / CBM）
  ├─ 目标国家
  ├─ HS 编码
  ├─ 申报价值（USD）
  ├─ 物流渠道（空运/海运整柜/海运拼柜/快递/直邮小包）
  └─ 目标售价（USD）

输出逐项成本：
  1. 采购成本          = 采购价 / 汇率
  2. 头程物流费        = 按渠道计费规则（重量计费 or 体积重取大者）
  3. 进口关税          = 申报价值 × 该国HS编码对应税率
  4. 进口环节税费      = 按目的国规则（如 VAT/GST/PPN）
  5. 报关清关固定费用  = 报关费 + MPF + ISF + 查验预备金
  6. 平台佣金          = 售价 × 平台佣金率（按类目不同）
  7. 支付手续费        = 售价 × 支付费率
  8. 平台物流费        = 按平台费率表（FBA/SLS 等）
  9. 广告费            = 售价 × 预估 ACOS
  10. 退货损失摊销     = 售价 × 退货率 × 损失率
  11. 仓储费           = 按体积×天数分摊
  12. 汇兑损益预备     = 成本合计 × 汇率波动预备率
  ─────────────────────────────────────────
  Landed Cost（到手总成本）= 1+2+3+4+5+11+12
  净利 = 售价 - Landed Cost - 6-7-8-9-10
  净利率 = 净利 / 售价
  保本售价 = Landed Cost + 6~10 项中与售价挂钩部分的临界点
```

**关键实现要求**：

| 要求 | 说明 |
|---|---|
| 税率数据可追溯 | 每个税率必须记录来源、生效日期、录入人 |
| 计算过程可解释 | 每项成本可展开查看计算式与引用的参数 |
| 支持情景模拟 | 可对比"空运 vs 海运""美国仓 vs 直邮"两种方案的总成本 |
| 精度要求 | 金额用 `Decimal` 存储与计算，禁用 float |
| 历史可重算 | 税率或汇率更新后，可对历史订单按新参数重算用于复盘 |

### 8.3 多租户设计

**三种方案对比**：

| 方案 | 隔离级别 | 成本 | 运维复杂度 | 适用 |
|---|---|---|---|---|
| 独立数据库 | 最高 | 最高 | 高（N 个库要迁移） | 大客户私有化 |
| 独立 Schema | 高 | 高 | 中 | 中等规模租户 |
| **共享表 + tenant_id（选定）** | 逻辑隔离 | 最低 | 最低 | SaaS 起步期 |

**决策：V1 采用共享表 + `tenant_id` 字段隔离**，理由是最低运维成本支撑快速迭代；同时对大客户预留"专属 schema"升级路径。

**隔离实现的三道防线**（必须有，否则数据串租户是灾难级事故）：

1. **第一道：ORM 层自动注入**
   通过 SQLAlchemy 的 `SessionEvent` / 自定义 `Query` 类，在编译 SQL 前自动为所有含 `tenant_id` 的表追加过滤条件，开发者无需手写。

```python
# app/core/tenant_isolation.py（示意）
from sqlalchemy import event
from sqlalchemy.orm import with_loader_criteria

TENANT_AWARE_MODELS = {Product, Order, Inventory, ...}

@event.listens_for(Session, "do_orm_execute")
def _inject_tenant_filter(execute_state):
    if execute_state.is_select and not execute_state.execution_options.get("skip_tenant"):
        tenant_id = current_tenant_id()          # 从 contextvar 取当前租户
        for model in TENANT_AWARE_MODELS:
            execute_state.statement = execute_state.statement.options(
                with_loader_criteria(model, lambda cls: cls.tenant_id == tenant_id,
                                     include_aliases=True)
            )
```

2. **第二道：数据库行级安全（RLS）兜底**
   在 PostgreSQL 上为租户表启用 Row Level Security，作为 ORM 漏写时的最后防线：

```sql
ALTER TABLE "order" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation_policy ON "order"
  USING (tenant_id = current_setting('app.current_tenant')::bigint);
```

3. **第三道：自动化测试守护**
   编写"租户越权测试"作为 CI 必跑用例：以租户 A 身份查询，断言返回结果中不含任何租户 B 的数据。**任何新增租户表都必须补充该测试。**

**租户上下文传递**：请求进入时由中间件解析 JWT → 写入 `contextvar` → 全链路可用（含 Celery 任务需在任务参数中显式传 tenant_id，因为跨进程 contextvar 不共享）。

### 8.4 ★ 平台适配器层（Platform Adapter Layer）

**这是整个系统最重要的架构决策。** 四个平台在认证方式、签名算法、字段命名、状态枚举、限流规则上完全不同。若让业务代码直接调用各平台 SDK，会出现大量 `if platform == 'shopee'` 散落各处，新增平台时改动面失控。

**设计目标**：新增一个平台，只需新增一个适配器实现类 + 一份字段映射配置，**业务层代码零改动**。

**统一领域模型（领域层只认这套模型）**：

```python
# app/adapters/base.py
from abc import ABC, abstractmethod
from dataclasses import dataclass
from datetime import datetime
from decimal import Decimal

# ---------- 统一领域模型 ----------
@dataclass
class UnifiedOrder:
    platform: str
    shop_id: str
    platform_order_id: str
    platform_status: str          # 平台原始状态
    unified_status: str           # 统一状态：PAID / SHIPPED / ...
    buyer_name: str | None
    buyer_country: str | None
    currency: str
    total_amount: Decimal
    items: list["UnifiedOrderItem"]
    paid_at: datetime | None
    updated_at: datetime
    raw: dict                     # 原始报文，全量保留便于审计与回溯

@dataclass
class UnifiedOrderItem:
    platform_sku_id: str
    platform_product_id: str
    quantity: int
    unit_price: Decimal
    item_name: str

# ---------- 适配器抽象接口 ----------
class PlatformAdapter(ABC):
    """所有平台适配器的统一契约。业务层只依赖此接口。"""

    platform: str

    # --- 认证 ---
    @abstractmethod
    def build_auth_url(self, redirect_uri: str, state: str) -> str: ...

    @abstractmethod
    async def exchange_token(self, code: str, shop_id: str | None) -> "TokenBundle": ...

    @abstractmethod
    async def refresh_token(self, cred: "PlatformCredential") -> "TokenBundle": ...

    # --- 数据拉取 ---
    @abstractmethod
    async def fetch_orders(self, cred, *, since: datetime, until: datetime,
                           cursor: str | None = None) -> "PageResult[UnifiedOrder]": ...

    @abstractmethod
    async def fetch_products(self, cred, *, cursor: str | None = None) -> "PageResult[UnifiedProduct]": ...

    @abstractmethod
    async def fetch_inventory(self, cred, *, sku_ids: list[str]) -> list["UnifiedInventory"]: ...

    # --- 数据写回 ---
    @abstractmethod
    async def publish_product(self, cred, product: "UnifiedProduct") -> "PublishResult": ...

    @abstractmethod
    async def update_price(self, cred, items: list["PriceUpdate"]) -> "BatchResult": ...

    @abstractmethod
    async def update_inventory(self, cred, items: list["InventoryUpdate"]) -> "BatchResult": ...

    @abstractmethod
    async def ship_order(self, cred, order_id: str, carrier: str, tracking_no: str) -> None: ...

    # --- 元信息 ---
    @abstractmethod
    def rate_limit(self) -> "RateLimitSpec":
        """返回该平台的限流规格：QPS、突发、维度（按店/按App）、批量上限"""

    @abstractmethod
    def status_mapping(self) -> dict[str, str]:
        """平台状态 → 统一状态 的映射表（可被数据库配置覆盖）"""

    def normalize_error(self, exc: Exception) -> "PlatformError":
        """把平台各式各样的错误统一成标准错误对象（含是否可重试）"""
        ...
```

**适配器注册与调用（工厂 + 注册表模式）**：

```python
# app/adapters/registry.py
_REGISTRY: dict[str, type[PlatformAdapter]] = {}

def register(cls: type[PlatformAdapter]) -> type[PlatformAdapter]:
    _REGISTRY[cls.platform] = cls
    return cls

def get_adapter(platform: str, *, tenant_id: int) -> PlatformAdapter:
    if platform not in _REGISTRY:
        raise UnsupportedPlatformError(platform)
    return _REGISTRY[platform](tenant_id=tenant_id)

# app/adapters/shopee/adapter.py
@register
class ShopeeAdapter(PlatformAdapter):
    platform = "shopee"
    ...
```

**业务层调用示例（完全不知道 Shopee 的存在）**：

```python
async def sync_shop_orders(shop: Shop, since: datetime, until: datetime):
    adapter = get_adapter(shop.platform, tenant_id=shop.tenant_id)
    cred = await credential_service.get(shop.id)
    async for page in paginate(adapter, cred, since=since, until=until):
        for uo in page.items:
            await order_service.upsert_from_unified(uo)   # 业务逻辑统一
```

**字段映射外置**：平台字段与统一字段的映射关系（尤其状态枚举、类目属性）不写在 Python 里，而是存放于数据库配置表 `platform_field_mapping`，运营可在后台维护。**当平台新增订单状态时，运营配置即可，无需发版。**

**适配器实现的共同要求**：
- 全量保留原始响应报文（`raw` 字段），便于问题排查与历史回溯。
- 所有对外调用必须经过统一限流器（见 8.5），不得直连。
- 错误统一转换：区分"可重试"（超时、429、5xx）与"不可重试"（401、参数错误、业务拒绝）。

### 8.5 ★ 数据同步引擎

**核心挑战**：平台 API 限流严格、网络不稳定、数据量大、多店铺并发、单平台故障不能拖垮全局。

**总体设计：事件驱动 + 分级队列 + 独立限流**

```
触发源
 ├─ Celery Beat 定时（订单 1min、商品 30min、库存 5min、广告 6h、财务 每日）
 ├─ 平台 Webhook（订单/库存变动实时推送）
 └─ 用户手动触发
        ↓
  任务分片（按 tenant × shop 切分，避免大店铺阻塞小店铺）
        ↓
  调度入队（Redis List / RabbitMQ，按平台分队列）
        ↓
  ┌──────────────────────────────────────────────────┐
  │ 每个「平台 × 店铺」一个独立的限流器实例            │
  │ 基于 Redis 令牌桶：                                │
  │   key = rl:{platform}:{shop_id}                   │
  │   速率与突发来自 platform_rate_limit 配置表         │
  └──────────────────────────────────────────────────┘
        ↓
  调用平台 API（超时 10s，指数退避重试 3 次）
        ↓
  ├─ 成功 → 归一化为统一模型 → 幂等写入
  ├─ 429 / 超时 / 5xx → 退避重试（1s, 4s, 16s + 抖动）
  └─ 重试耗尽 → 死信队列 DLQ + 告警，保留原始请求参数以便人工重放
```

**增量同步策略（游标 + 状态双保险）**：

| 数据类型 | 同步方式 | 增量依据 | 频率 |
|---|---|---|---|
| 订单 | 游标增量 + Webhook | `update_time` 游标 + 重叠窗口 5 分钟 | 1 分钟 |
| 商品 | 游标全量对比 | 分页游标 + 平台侧 `update_time` 比对 | 30 分钟 |
| 库存 | 双向（本地为主） | 按 SKU 批量拉取 | 5 分钟 |
| 广告 | 按日快照 | 日期维度报表接口 | 6 小时 |
| 财务账单 | 按结算周期拉取 | settlement_id 游标 | 每日 |
| 消息 | 游标 + Webhook | 消息 ID 游标 | 5 分钟 |

> **重叠窗口（overlap window）**：增量拉取时向前多取 5 分钟，防止因平台侧数据延迟更新或写入时序问题导致漏单。配合幂等键去重，多拉的数据不会产生重复。

**幂等三件套**（保证重复拉取不产生脏数据）：

1. **幂等键**：`{platform}:{shop_id}:{platform_id}`，写入数据库唯一索引。
2. **UPSERT 语义**：`INSERT ... ON CONFLICT (idempotency_key) DO UPDATE`，且仅当源数据 `updated_at` 更新时才覆盖。
3. **Redis 布隆过滤器**：前置快速判重，减少 DB 压力（可容忍极低误判率，最终由 DB 唯一索引兜底）。

**限流与配额管理**（`platform_rate_limit` 配置表）：

| 配置项 | 说明 | 示例值 |
|---|---|---|
| platform | 平台 | shopee |
| dimension | 限流维度 | per_shop / per_app / per_endpoint |
| qps | 每秒请求数 | 2 |
| burst | 突发容量 | 10 |
| daily_quota | 日配额 | 100000 |
| batch_limit | 单次批量上限 | 50 |
| concurrency | 建议并发数 | 3 |

> ⚠️ **再次强调**：以上数值仅作示例。各平台公布口径不一致且会调整，**上线前必须以平台开发者后台显示的实时配额为准录入配置**，并实现"命中 429 自动降速"的自适应机制（连续 429 时自动将 QPS 下调 50% 并持续观察）。

**故障隔离（NFR-A-06 的实现）**：

- 按平台划分独立队列与独立 Worker 池 → 某平台 API 大面积超时只耗尽自己的 Worker。
- 熔断器（Circuit Breaker）：某平台连续失败率 >50% 时熔断 5 分钟，期间直接快速失败，不再打给平台（避免被封 IP）。
- 降级标识：同步失败的店铺在前端明确标注"数据更新于 X 时间，可能不是最新"，而不是静默展示旧数据。

**同步任务的状态与可观测性**：

```
SyncTask: PENDING → RUNNING → (SUCCESS | PARTIAL | FAILED)
   ├─ 记录：拉取条数、新增、更新、跳过、失败、耗时、平台调用次数
   ├─ 记录：命中限流次数、重试次数
   └─ 保留最近 30 天，前端可视化
```

### 8.6 异步任务与调度

**任务分类与队列优先级**：

| 队列 | 优先级 | 用途 | Worker 配置 |
|---|---|---|---|
| `high` | 10 | 用户交互触发的任务（手动同步、导出） | 并发 8 |
| `sync` | 5 | 平台数据同步 | 并发按平台分配 |
| `batch` | 3 | 批量刊登、批量改价 | 并发 4 |
| `report` | 1 | 报表生成、预聚合 | 并发 2 |
| `dlq` | — | 死信队列，人工处理 | 不自动消费 |

**定时任务清单（Celery Beat）**：

| 任务 | 频率 | 说明 |
|---|---|---|
| `refresh_platform_tokens` | 每 10 分钟 | 扫描即将过期的令牌并刷新 |
| `sync_orders_incremental` | 每 1 分钟 | 按店铺分发增量订单同步 |
| `sync_inventory_push` | 每 5 分钟 | 库存回传平台 |
| `sync_products` | 每 30 分钟 | 商品与 Listing 状态巡检 |
| `sync_ads_daily` | 每日 03:00 | 广告数据拉取 |

| `calc_sku_profit` | 每日 05:00 | SKU 利润重算 |

| `cleanup_expired_data` | 每日 02:00 | 清理过期日志与导出文件 |

**任务可靠性要求**：
- 所有任务必须幂等（重复执行结果一致）。
- 必须设置 `acks_late=True` + `reject_on_worker_lost=True`，防止 Worker 崩溃丢任务。
- 必须设置任务超时（防止卡死占用 Worker）。
- 定时任务使用 Redis 分布式锁防止多实例重复触发。

## 9. 数据库设计

### 9.1 设计原则

| 原则 | 具体约定 |
|---|---|
| 主键 | 统一使用 `BIGINT` + Snowflake/号段生成（避免自增 ID 暴露业务规模） |
| 租户字段 | 所有业务表必须含 `tenant_id BIGINT NOT NULL` 并建索引 |
| 审计字段 | 所有表含 `created_at`、`updated_at`、`created_by`、`updated_by` |
| 软删除 | 业务主数据用 `deleted_at TIMESTAMPTZ NULL`；流水表不删除 |
| 金额 | `NUMERIC(20,6)`，禁用 float/double |
| 币种 | 每笔金额必须伴随 `currency CHAR(3)` 字段 |
| 时间 | 统一 `TIMESTAMPTZ`，存 UTC |
| 枚举 | 用 `SMALLINT` + 代码内常量表（比 VARCHAR 省空间且索引友好） |
| 命名 | 表名单数蛇形（`order_item`），避免 SQL 保留字（订单表用 `sales_order`） |
| JSON 字段 | 平台原始报文、扩展属性用 `JSONB` + GIN 索引 |
| 分区 | `order_item`、`inventory_flow`、`audit_log` 按月分区 |

> ⚠️ **注意**：`order` 是 SQL 保留字，订单主表命名为 **`sales_order`**；`user` 同样是保留字，用户表命名为 **`sys_user`**。

### 9.4 索引与分区策略

| 策略 | 适用表 | 说明 |
|---|---|---|
| 索引前缀原则 | 所有业务表 | 索引首列必须为 `tenant_id`（多租户查询必带） |

| BRIN 索引 | 超大日志表的时间列 | 体积小，范围查询高效 |

```json
    }
  }
}
```

> **设计要点**：每一项成本都必须带 `formula`（计算式）与 `source`（数据来源）。这既满足用户"为什么是这个数"的追问，也让开发调试与财务核对变得可行。**任何不可解释的成本数字都是不可信的数字。**

### 10.5 平台 Webhook 接收设计

```
POST /api/v1/webhooks/{platform}

处理流程：
① 验签（各平台签名算法不同，由适配器实现）
② 立即返回 200（避免平台重推）—— 严禁在 Webhook 里做重量级处理
③ 原始报文写入 Redis 队列 → 异步处理
④ 按事件类型路由：
   order.status_changed → 更新订单状态
   order.created        → 拉取订单详情
   inventory.changed    → 触发库存对账
   message.created      → 拉取客服消息
⑤ 幂等：事件 ID 去重（Redis Set，TTL 24h）
⑥ 失败进 DLQ，保留原始报文以便重放
```

**Webhook 安全要求**：验签失败直接丢弃并记日志；限制来源 IP（若平台提供）；限流防刷（单平台每秒最多 100 次）。

### 10.6 开放 API 与配额

| 套餐 | 请求配额 | 说明 |
|---|---|---|
| 免费版 | 1,000 次/天 | 单店铺 |
| 专业版 | 50,000 次/天 | ≤5 店铺 |

## 12. 安全与风控

### 12.1 数据安全

| 风险 | 措施 |
|---|---|
| 租户数据串号 | 三道防线（ORM 自动注入 + RLS + CI 越权测试），见 8.3 |
| 平台密钥泄露 | AES-256-GCM 字段级加密，密钥由 KMS 管理，禁止进代码与日志 |
| 日志泄露隐私 | 日志脱敏：手机号 `138****8888`、地址仅保留国家/城市 |
| 数据导出滥用 | 导出需权限 + 二次确认 + 全量导出限速 + 导出行为审计 |
| 备份泄露 | 备份加密存储，访问需审批 |
| 买家信息越权查看 | 按角色分级脱敏（见 F4 脱敏规则表） |

### 12.2 接口安全

| 风险 | 措施 |
|---|---|
| 越权访问 | 每个接口强制校验 `资源归属租户` + `用户数据范围`，不做"只靠前端隐藏" |
| 水平越权（改 ID 访问他人数据） | 所有按 ID 查询必须带 `tenant_id` 条件（由 Repository 层强制） |
| 接口刷取 | 按租户 + 按 IP 双维度限流；敏感接口（登录、导出、计算）单独限流 |
| 重放攻击 | 开放 API 要求时间戳（±5 分钟）+ nonce 去重 |
| 爬虫抓取 | 验证码（异常时触发）+ UA 校验 + 行为分析 |
| 批量操作被滥用 | 单次批量上限（500）+ 大批量走异步 + 频率限制 |

### 12.3 平台侧风控（合规红线，直接关系用户账号安全）

> 这一段是产品必须主动承担的合规责任。**系统绝不能提供任何帮助用户违规的功能。**

| 红线 | 系统约束 |
|---|---|
| 禁止刷单/刷评 | 不提供任何虚假订单、虚假评价、Vine 违规操作功能 |
| 禁止多账号关联规避 | 不提供帮助规避平台账号关联检测的功能 |
| 禁止低报申报价值 | 申报价值合规提醒（申报价 vs 售价偏差 >20% 告警）；不提供"申报价拆分"工具 |
| 禁止侵权商品 | 品牌库 + 禁售词扫描 + 平台品牌备案状态记录 |
| 禁止自动化广告操纵 | V1 完全关闭平台广告写接口 |
| 数据获取合规 | 仅通过平台官方开放 API 获取数据，不做违规爬虫与数据买卖 |

### 12.4 业务风控

| 风险 | 措施 |
|---|---|
| 库存超卖 | 三层防超卖机制（见 5.3） |
| 成本算错导致亏本定价 | 成本项缺失时计算结果标记为"不完整"并拒绝给出建议售价 |
| 汇率波动导致亏损 | 汇兑预备金参数 + 汇率异常波动（日波动 >3%）告警 |
| 认证过期导致下架 | 三级到期预警（60/30/7 天） |
| 同步失败导致数据失真 | 数据陈旧显性标识，绝不静默展示旧数据 |
| 误操作不可恢复 | 批量操作预览 + 二次确认 + 关键操作可回滚 + 操作日志 |

## 13. 测试策略

### 13.1 测试分层与覆盖目标

| 层级 | 范围 | 工具 | 覆盖率目标 |
|---|---|---|---|
| 单元测试 | 核心算法（Landed Cost、利润核算、状态机、限流器） | pytest / vitest | ≥ 80% |
| 集成测试 | API 接口、数据库事务、适配器（Mock 平台） | pytest + httpx | ≥ 70% |
| E2E 测试 | 关键用户路径（授权→刊登→订单→发货） | Playwright | 覆盖 8 条主路径 |
| 契约测试 | 平台适配器与统一模型的映射正确性 | pytest + 真实报文样本 | 100%（各平台样本） |
| 性能测试 | 核心接口与批量操作 | Locust | 达标 NFR-P 全部指标 |
| 安全测试 | 越权、注入、限流绕过 | 人工 + OWASP ZAP | — |

### 13.2 必须覆盖的高危测试用例

**多租户隔离类（P0 必测）**：
1. 以租户 A 的令牌请求 `/orders/{租户B的订单ID}` → 必须返回 404 而非 403（不泄露存在性）。
2. 列表接口无论如何构造筛选参数，返回结果不含其他租户数据。
3. 导出接口不导出其他租户数据。
4. 新增租户表后，越权测试必须补充并通过。

**幂等与去重类（P0 必测）**：
1. 同一订单通过轮询与 Webhook 双通道到达 → 只入库一条。
2. 同一同步任务重复执行 → 数据无变化、无重复流水。
3. 幂等键冲突时按 `updated_at` 正确判断是否更新。

**库存一致性类（P0 必测）**：
1. 并发 100 单同时扣减同一 SKU → 库存不为负，成功率与库存数匹配。
2. 订单取消后库存正确释放。
3. 退货入库后库存正确恢复。
4. 平台回传失败进入重试队列，最终一致。

**计算正确性类（P0 必测）**：
1. Landed Cost 各项计算与手工核对结果一致（用真实案例做黄金测试集）。
2. 印尼 11/12 计税基础等特殊规则正确。
3. 多币种换算按指定汇率口径正确。
4. 金额计算无浮点误差（全链路 Decimal）。

**限流与容错类（P1 必测）**：
1. 模拟平台返回 429 → 自动退避且不丢失任务。
2. 模拟平台持续 5xx → 熔断生效，不影响其他平台。
3. Worker 崩溃 → 任务不丢失（acks_late 生效）。
4. Token 过期 → 自动刷新成功。

### 13.3 平台适配器的测试方案

由于真实平台 API 无法在 CI 中稳定调用，采用**三层测试策略**：

| 层级 | 方式 | 用途 |
|---|---|---|
| 单元层 | 用录制的真实响应报文（fixture）测试字段映射 | 快速验证归一化逻辑 |
| 集成层 | 平台 Sandbox 环境（Shopee/Amazon 均提供） | 验证签名、认证流程 |
| 冒烟层 | 自有测试店铺的真实调用（每日定时） | 捕获平台接口变更 |

> **关键保障**：各平台真实响应报文必须**录制并纳入版本库**（脱敏后），这是防止"平台悄悄改字段导致线上故障"的唯一可靠手段。

### 17.2 平台 API 接入速查

| 平台 | 开发者平台 | 认证方式 | 令牌有效期 | 主要注意点 |
|---|---|---|---|---|
| Amazon | Selling Partner API (SP-API) | LWA OAuth 2.0 + AWS SigV4 | Access 1h | 需 AWS 账号与 IAM Role；订单接口频率极低，需批量+缓存；Feeds 异步处理可能耗时 15–30 分钟 |
| Shopee | Shopee Open Platform | partner_id + partner_key + HMAC-SHA256 + timestamp | 4h（需 refresh） | 时间戳须 UTC 且服务器时钟同步；IP 白名单；限流按店铺维度 |
| Lazada | Lazada Open Platform | app_key + app_secret + OAuth 2.0 | 7 天（refresh 窗口 30 天） | 限流严格，库存更新需批量；官方 SDK `lazop-sdk` 可处理签名 |
| TikTok Shop | TikTok Shop Partner Center | OAuth 2.0 + 签名 | 依官方文档 | **强制 IP 白名单**，需提前登记服务器出口 IP |

**接入通用避坑清单**：

- [ ] 服务器时钟与 NTP 同步（时间戳偏差 >15 分钟直接认证失败）
- [ ] 出口 IP 提前加入各平台白名单（TikTok 强制）
- [ ] 令牌自动刷新任务先于其他功能上线
- [ ] 先在 Sandbox 环境跑通全流程再切生产
- [ ] 每个接口都实现重试与 429 处理，不做裸调用
- [ ] 记录每次调用的 request_id / trace_id，便于向平台提工单
